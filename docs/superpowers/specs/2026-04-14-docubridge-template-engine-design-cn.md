# DocuBridge 模板排版引擎升级设计

> 日期：2026-04-14  
> 适用范围：`Markdown -> Word (.docx)`  
> 目标读者：产品负责人、开发人员、模板实施人员

## 1. 背景

当前 `Markdown -> Word` 的模板能力已经能覆盖最小可用场景：

- 通过 `--template` 提供宿主 `.docx`
- 通过 `--style` 指定 Markdown 元素与 Word 样式的映射
- 对标题、正文、列表、引用、表格、代码块等结构进行基础样式绑定

但这套实现仍然更接近“样式映射器”，还不是“相对完整的 Word 模板排版引擎”。

当前已确认的核心缺口包括：

- 模板中的默认样式只能部分体现，支持面过窄
- 编号体系仍以文本前缀模拟为主，不能完整复用 Word 编号定义
- 段落属性支持不完整，无法稳定覆盖首行缩进、段前段后、对齐等需求
- 中英文字体槽位未被系统化支持
- 模板、YAML、默认值的合并逻辑还不足以支撑复杂企业模板

因此，需要对 `Markdown -> Word` 侧的模板能力进行架构升级。

## 2. 目标

本次升级后的目标不是“再补几个字段”，而是建立一套新的模板排版引擎主链路。

目标能力如下：

1. 模板中的默认样式必须真实生效
2. YAML 负责映射、覆盖和局部增强
3. 模板负责基础样式、宿主样式和编号资源
4. 支持中英文字体分开设置
5. 编号体系尽量完整复用 Word 模板定义
6. 段落属性可配置并可落地
7. `doctor` / `style explain` 能解释最终生效结果

这套引擎采用：

- `混合模式`

即：

- 模板提供真实 Word 样式和编号体系
- YAML 提供结构映射和显式 override
- 二者共同决定最终输出

## 3. 非目标

本阶段不追求以下内容：

- 页眉页脚完整模板恢复
- 节分隔与复杂分页的完整还原
- 目录域自动高级恢复
- 脚注、尾注、批注系统完整渲染
- 完整覆盖 Word 所有版式能力

这些内容可以在后续阶段继续扩展，但不作为当前模板排版引擎骨架阶段的必达目标。

## 4. 设计原则

### 4.1 不再继续打补丁

当前实现里，列表、编号、模板样式读取等逻辑已经有明显的“功能点叠加”倾向。  
继续在现有渲染器上追加补丁，会让复杂模板场景越来越难维护。

因此，本次升级采用新的分层结构，不沿用“局部小修”的方式扩展模板能力。

### 4.2 先建立中间排版模型

Markdown 节点不应直接驱动最终 Word 写入。  
应先转为一套“排版意图模型”，再由模板与规则系统决定最终落地方式。

### 4.3 模板和 YAML 必须可解释

用户最终关心的是：

- 为什么输出成这样
- 某个属性到底来自模板还是 YAML
- 某个编号为什么没有按预期生效

因此，新引擎从设计上必须支持诊断与解释，而不是只支持渲染。

### 4.4 Word 原生能力优先

对于编号、段落、字体槽位等能力，优先采用 Word 原生结构落地，而不是文本模拟。

## 5. 总体架构

建议将新的模板排版引擎拆为 5 层。

### 5.1 模板读取层

负责从 `.docx` 模板中读取：

- 段落样式
- 字符样式
- 文档默认样式
- 段落属性
- 字体槽位
- 编号定义
- 多级编号结构

输出结果是一份新的模板视图对象，不再只包含少量 `font_name` / `font_size`。

### 5.2 排版意图模型层

负责把 Markdown 解析结果转换成统一的排版意图对象。

排版意图对象至少需要表达：

- 块级元素类型
- 目标段落类型
- 目标字符样式意图
- 目标编号意图
- 段落属性意图
- 字体属性意图
- 表格和代码块宿主规则

这一层不直接关心 Word API，只负责表达“我要什么效果”。

### 5.3 规则合并层

负责合并：

- 模板默认值
- 模板中的具体 Word 样式
- YAML 元素映射
- YAML 显式 override
- 系统默认兜底值

输出结果是一份“最终生效排版规则”。

### 5.4 编号引擎

负责：

- 标题编号
- 列表编号
- 多级编号
- 续号
- 不同编号格式
- 模板编号定义映射

编号引擎是单独模块，不再只是列表渲染里的局部逻辑。

### 5.5 Word 写入层

最终负责：

- 写入段落样式
- 写入字符样式
- 写入字体槽位
- 写入段落属性
- 写入真实编号绑定
- 写入表格与代码块

## 6. 模板读取层详细要求

### 6.1 样式读取

应至少读取：

- 样式名称
- 样式类型（段落 / 字符 / 表格）
- 基于哪个样式
- 字体相关属性
- 段落相关属性

### 6.2 字体槽位

必须支持中英文字体分开设置。

至少要考虑：

- East Asia 字体
- ASCII 字体
- HAnsi 字体
- Complex Script 字体（如后续需要）

对用户可见的配置层面，至少应表达为：

- 中文字体
- 英文字体

底层再映射到 Word 对应字体槽位。

### 6.3 段落属性

至少应支持读取并建模：

- 首行缩进
- 左右缩进
- 段前
- 段后
- 行距
- 对齐方式
- 分页控制相关基础属性（可作为后续扩展）

### 6.4 编号定义

必须读取模板中的：

- abstract numbering
- numbering instance
- 多级层级定义
- 各级编号格式
- 起始值
- 续号关系

这是后续复用模板编号体系的基础。

## 7. 排版意图模型设计

建议引入独立的排版意图对象，例如：

- `DocumentLayoutIntent`
- `ParagraphLayoutIntent`
- `RunStyleIntent`
- `NumberingIntent`
- `TableLayoutIntent`

其中 `ParagraphLayoutIntent` 至少应包含：

- element_name
- target_word_style
- paragraph_properties
- numbering_intent
- inline_style_runs

`NumberingIntent` 至少应包含：

- numbering_role（heading / ordered_list / unordered_list）
- level
- continue_sequence
- preferred_template_numbering
- fallback_strategy

## 8. 规则合并逻辑

### 8.1 合并顺序

推荐合并顺序如下：

1. 系统默认值
2. 模板文档默认样式
3. 模板中的具体 Word 样式
4. YAML 元素映射
5. YAML 显式 override

### 8.2 结果解释

最终每个属性都应能解释来源：

- `default`
- `template_document_default`
- `template_style`
- `yaml`
- `yaml_override`

### 8.3 诊断支持

`style explain` 后续应不仅能展示字体和字号，还应能展示：

- 中文字体 / 英文字体来源
- 段落属性来源
- 编号资源来源
- 是否使用模板编号定义

## 9. 编号引擎设计

### 9.1 当前问题

当前列表更多是：

- 段落样式 + 文本前缀

这不符合正式 Word 模板要求。

### 9.2 新目标

编号引擎必须支持：

- 标题编号
- 普通多级列表编号
- 不同编号格式
- 模板定义复用
- 续号
- 层级控制

### 9.3 标题编号

目标是让标题编号尽量走模板中的真实编号定义，而不是在文本里手动拼接。

### 9.4 列表编号

目标是让普通有序列表也能走模板中的真实编号资源。

### 9.5 回退策略

如果模板中缺失必要编号定义，系统应：

- 给出明确诊断
- 允许安全回退
- 但不能静默伪装成“已完整支持”

## 10. 段落与字体支持范围

### 10.1 第一阶段必须支持

- 中文字体
- 英文字体
- 字号
- 加粗
- 斜体
- 首行缩进
- 左右缩进
- 段前
- 段后
- 对齐方式

### 10.2 第二阶段可继续扩展

- 制表位
- 孤行控制
- 与下段同页
- 段中不分页
- 更复杂的分页控制

## 11. 第一阶段实施范围

第一阶段采用“编号体系 + 段落/字体体系并行，先做可贯通骨架”的策略。

第一阶段必须打通：

1. 模板样式真实绑定
2. 中英文字体分槽位设置
3. 基础段落属性落地
4. 标题编号走真实编号体系
5. 普通有序列表走真实编号体系
6. `doctor` / `style explain` 能解释这些结果

## 12. 验收标准

第一阶段验收至少包括以下项目。

### 12.1 模板样式

- 标题、正文、列表、引用、表格、代码块能绑定模板样式

### 12.2 字体

- 中文字体与英文字体可分别配置并落地

### 12.3 段落

- 首行缩进、段前、段后、对齐至少能在主链路中生效

### 12.4 编号

- 标题编号走模板编号体系
- 普通有序列表走模板编号体系
- 多级编号基本可用

### 12.5 诊断

- `style explain` 能解释最终编号与段落规则来源

## 13. 风险

### 13.1 编号体系复杂度高

Word 编号体系本身较复杂，尤其是：

- abstract numbering
- numbering instance
- 样式绑定
- 续号

需要单独测试矩阵支持。

### 13.2 模板差异大

不同企业模板质量差异很大，命名不规范、样式继承混乱的情况很常见。

因此诊断能力必须同步建设。

### 13.3 现有渲染器耦合度

当前渲染器逻辑偏直接生成，需要逐步引入中间层，不能一次性硬切换导致主链路失稳。

## 14. 建议后续动作

下一步建议不是直接编码，而是先写实现计划。

建议计划至少拆成：

1. 模板读取层重构
2. 排版意图模型引入
3. 规则合并层重构
4. 编号引擎实现
5. 段落与字体槽位落地
6. 诊断能力升级

## 15. 结论

当前 `Markdown -> Word` 的模板能力已经不足以支撑“文档标准可配置”的目标。  
本设计将其升级为一套新的混合模式模板排版引擎：

- 模板提供真实 Word 样式和编号资源
- YAML 提供映射、覆盖和局部增强
- 引擎负责合并、解释与落地

第一阶段以“编号体系 + 段落/字体体系并行，先打通骨架”为目标。
